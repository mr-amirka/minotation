# minotation-runtime

DOM-рантайм [minotation](../core): компилирует токены прямо в браузере, без
сборки и без плагина сборщика.

```bash
pnpm add minotation minotation-runtime
```

## Зачем

Обычный путь — плагин сборщика: он сканирует исходники и кладёт готовый CSS в
бандл. Но токены не всегда известны на этапе сборки:

- разметка приходит с сервера или из CMS;
- классы собираются в рантайме из данных;
- страница редактируется пользователем (конструктор, превью, песочница);
- виджет встраивается в чужую страницу, где сборки нет вовсе.

Здесь и нужен рантайм: он смотрит на итоговый DOM и компилирует то, что в нём
действительно есть.

## Быстрый старт

```ts
import { minotationProvider, presetStandard, presetSynonyms } from 'minotation';
import { createMnRuntime } from 'minotation-runtime';

const mn = minotationProvider();
mn.setPresets([presetStandard, presetSynonyms]);

const runtime = createMnRuntime(mn);
// с этого момента любой <div class="p10 dF"> в документе получит свои стили

// при размонтировании приложения:
runtime.stop();
```

Рантайм сканирует текущий DOM, компилирует найденные токены и дальше следит за
изменениями через `MutationObserver`: новые узлы и правки атрибута попадают в
CSS сами.

## API

### `createMnRuntime(mn, options?) → MnRuntimeHandle`

`mn` — инстанс `minotationProvider()` с уже загруженными пресетами.

| Опция | По умолчанию | Что делает |
|-------|--------------|------------|
| `attr` | `'class'` | атрибут, из которого берутся токены |
| `root` | `document` | корень наблюдения — документ или элемент |
| `styleAttr` | `'data-mn-runtime'` | маркер на инжектируемом `<style>` |

Возвращает `{ stop() }` — останавливает наблюдение и отписывается от стилей.
Вызывать повторно безопасно.

**Про `styleAttr`.** Имя отличается от `data-mn`, которым помечают свой тег
плагины сборщиков. Так рантайм и сборка не затирают стили друг друга, если в
проекте включены оба пути сразу.

**Про `root`.** Ограничивает наблюдение поддеревом — например, одним виджетом
на чужой странице. Всё, что снаружи, рантайм не трогает.

## Почему `MutationObserver`, а не патч рендера

В 1.x перехватывался `React.createElement` и сканировался `props.className`.
Такой подход ломается, как только рендер идёт мимо этого вызова — а именно это
и происходит с automatic JSX runtime (`"jsx": "react-jsx"`, умолчание
современных сборок): JSX компилируется в `jsx()`/`jsxs()` из
`react/jsx-runtime`, и `React.createElement` не вызывается вообще. Патч тогда
просто не срабатывает, молча.

Наблюдение за готовым DOM от способа рендера не зависит вовсе: React (обе
формы JSX), Vue, Angular, Svelte, Solid, серверный HTML, ванильный JS — DOM не
знает и не обязан знать, кто его создал.

## Адаптеры под фреймворки

Ядро фреймворк-агностично; адаптеры добавляют к нему привязку к жизненному
циклу компонента и изолированный iframe-виджет:

| Пакет | Что даёт |
|-------|----------|
| [`minotation-runtime-react`](../minotation-runtime-react) | хук `useMnRuntime`, `<MnIframe>` |
| [`minotation-runtime-vue`](../minotation-runtime-vue) | composable `useMnRuntime`, `<MnIframe>` |
| [`minotation-runtime-angular`](../minotation-runtime-angular) | директива `mnRuntime`, `<mn-iframe>` |

Свой адаптер пишется за десяток строк: запустить `createMnRuntime` при
монтировании, позвать `stop()` при размонтировании.

## Рантайм или плагин сборщика

| | рантайм | плагин сборщика |
|---|---|---|
| Когда собирается CSS | в браузере, по факту разметки | на этапе сборки |
| Токены из данных и CMS | видит | не видит |
| Цена | `MutationObserver` + компиляция на клиенте | ноль на клиенте |
| Нужна сборка | нет | да |

Одно другому не мешает: статику можно собрать плагином, а рантайм оставить для
динамической части — маркеры на `<style>` у них разные.
